# Restore-drill — протокол

Перевірка, що бекап справді відновлюється: `scripts/restore-drill.sh` бере останній
дамп, відновлює його у **чистий** контейнер `postgres:16-alpine` з новим порожнім volume
і порівнює контрольні значення з тими, що записав `scripts/backup.sh` у момент бекапу.

| Параметр | Значення |
|---|---|
| Дата drill | 2026-09-30 |
| Дамп | `backups/marketplace_2026-09-30_19-54-16.dump` (`pg_dump -Fc`) |
| Розмір дампу | 20 928 байт (≈ 20,4 КіБ) |
| Контрольні значення до | `15\|11\|18\|23\|6426650` (users\|products\|orders\|order_items\|sum(orders.total_amount_cents)) |
| Контрольні значення після | `15\|11\|18\|23\|6426650` |
| Результат | **MATCH** (exit 0; повторний запуск — теж MATCH) |
| Час `pg_restore` | 389 мс (другий прогін: 645 мс) |
| **RTO (виміряний)** | **≈ 4,5 с** (4480 мс від створення контейнера до звіреного checksum; другий прогін 4922 мс) |
| **RPO (розклад)** | **до 24 годин** |

## RTO

Виміряно на мікро-базі (20 КіБ, dev-машина): ~4,5 секунди, з яких ~4 с — старт
контейнера й `initdb`, а сам `pg_restore` — менше секунди. Це **нижня межа**: на
реальних даних час відновлення росте з розміром дампу (послідовне відтворення даних
та індексів), плюс час на підключення застосунку. Оцінка для прод-обсягу має бути
перемірена drill-ом на копії реального розміру — ця цифра лише доводить механіку.

## RPO

Бекап щоночі (`backup.cron`, 02:30) означає, що в найгіршому випадку (збій за хвилину до
наступного запуску) втрачається **майже 24 години** даних: усе, що записано після
останнього дампу. Чесний RPO цього розкладу — **24 години**. Щоб його зменшити, треба
частіші дампи (напр. щогодини → RPO 1 год) або WAL-архівація / PITR (RPO у секунди), що
виходить за рамки цього ДЗ.

## Як повторити

```
docker compose up -d --wait
bash scripts/with-secrets.sh dev bash scripts/backup.sh
bash scripts/with-secrets.sh dev bash scripts/restore-drill.sh   # -> MATCH
```
